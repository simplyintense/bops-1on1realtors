# 1on1 Realtors setup

This fork runs Bops for 1on1 Realtors (1on1realtors.com, Trinidad and Tobago).

## The team (lib/realty-team.ts)

A fresh start (or Start over) gets five bots, all on the main bot's computer. Names use the
Si.<Function> style for Simply Intense business bots.

| Bot | Role | What it does |
|---|---|---|
| Si.Leady (main, id `boppy`) | Lead bot, 1on1 Realtors | Takes requests and hands them to the specialists |
| Si.Clienty (id `clienty`) | Client and lead intake | New website leads (contact form + property inquiries), flags ones waiting over 24h, drafts first replies |
| Si.Listingy (id `listingy`) | Listings | Stale, unviewed or incomplete listings; matches CRM clients to listings |
| Si.Viewy (id `viewy`) | Viewings and showings | Tour/viewing requests, clashes, drafts confirmations |
| Si.Reporty (id `reporty`) | Weekly report | Monday report: leads, showings, clients, tasks, listings (facts only) |

`BOPS_TEAM_PRESET=bops` brings back upstream's Boppy alone. Nobody is contacted without the owner's OK.

## The CRM connector (lib/server/realty-crm.ts) — read-only stub

The realty_* tools (`realty_new_leads`, `realty_listings`, `realty_showings`, `realty_pipeline`) read the
site's Supabase backend over its REST API, signed in as a dedicated bot login so the CRM's row-level
security decides what they see. They are only offered when all of these are set in `.env.local`:

- `ONEON1_CRM_URL`, `ONEON1_CRM_ANON_KEY` (publishable key only, never the service-role key)
- `ONEON1_CRM_BOT_EMAIL`, `ONEON1_CRM_BOT_PASSWORD`

The chat tools never write. `ONEON1_CRM_WRITES=1` only lets the realty CLIs' `--apply` step insert
approved proposals (below). Wired into chat turns; computer tasks don't get
them yet.

## Hosting at bop.1on1realtors.com (not deployed yet)

The same Next server the Mac app ships, in a container (`Dockerfile`), with a login gate in front.
Two ready configs; pick one host:

- **Fly.io** (`fly.bop-1on1.toml`, region `mia`, 3 GB volume for `.data/`, one always-on machine):
  ```sh
  fly apps create bop-1on1realtors
  fly volumes create bops_data --size 3 --region mia -a bop-1on1realtors
  fly secrets set -a bop-1on1realtors BOPS_ALLOWED_EMAILS=... BOPS_GATE_SECRET=... GOOGLE_OAUTH_CLIENT_ID=... \
    GOOGLE_OAUTH_CLIENT_SECRET=... ORGO_API_KEY=... OPENAI_API_KEY=... OPENAI_EXECUTOR_API_KEY=... \
    ONEON1_CRM_URL=... ONEON1_CRM_ANON_KEY=... ONEON1_CRM_BOT_EMAIL=... ONEON1_CRM_BOT_PASSWORD=...
  fly deploy -c fly.bop-1on1.toml
  ```
  (Type the values in a terminal or the Fly dashboard. Never put them in this repo, a PR or a chat.)
- **Render** (`render.yaml`, a Blueprint: Docker web service + 3 GB disk). Secrets are `sync: false`,
  entered in Render's dashboard; `BOPS_GATE_SECRET` is generated by Render.

One instance only on either host: the state is a file on the volume, which two instances can't share.
(Upstream's Postgres mode, `BOPS_DATABASE_URL`, is for Bops Cloud's own multi-user hosting and isn't
used here.)

### Public demo on Vercel (demo data only)

A free Vercel project imported from this repo (framework Next.js, default `npm run build`) serves only the
demo page, `/realty-demo`: the bot team and the lead flow's simulated day on the fixture CRM (made-up people),
run in memory on each visit. Every other page redirects there and every other API call answers 403, so nobody
on the open web can sign the server in to Orgo, add keys or reach anything that sends. `/api/health` stays open.

- Demo mode (`publicDemo` in lib/gate.ts) is on whenever `VERCEL` is set (Vercel sets it), or with
  `ONEON1_PUBLIC_DEMO=1`. `ONEON1_PUBLIC_DEMO=0` turns it off; only do that with the login gate on and real hosting decided.
- No environment variables are needed. Optional: `ONEON1_LEAD_TIMEOUT_MINUTES` (answer window shown, default 15).
  Don't add Orgo, OpenAI, CRM, Gmail, AgentMail, phone or market-search keys to the demo project.
- On Vercel, `.data/` resolves to `/tmp/.data` (lib/server/user-paths.ts): only `/tmp` is writable there, and it doesn't last.
- Same flow locally: `npm run build && VERCEL=1 npm start`, then open `/realty-demo`.

### The login gate (lib/gate.ts, proxy.ts, app/api/gate/*)

`BOPS_LOGIN_GATE=google` (set in the image) puts Google sign-in in front of every page and API call.
Only emails on `BOPS_ALLOWED_EMAILS` get in (exact addresses, or `@1on1realtors.com` for the whole
domain); the list is checked on every request, so removing someone and restarting signs them out.
Sessions last 12 hours, in an httpOnly, Secure, SameSite=Lax cookie signed with `BOPS_GATE_SECRET`.
If the gate is on but a setting is missing, the server answers 503 to everyone (fails closed).
Open without sign-in: `/api/health` (says only `{"bops":true}`), the sign-in routes, and the webhook
paths that check their own signatures (`/api/apps/call`, `/api/phone/*`, `/api/channels/slack/events`,
`/api/cloud/event`). With the gate off (the Mac app, `npm run dev`), nothing changes from upstream.

Google OAuth client (in the 1on1 Realtors Google Cloud project): type "Web application", authorized
redirect URIs `https://bop.1on1realtors.com/api/gate/callback` and, until DNS is live,
`https://bop-1on1realtors.fly.dev/api/gate/callback` (or the onrender.com name). Scopes: `openid email`.

### DNS (for AWS Bot, when the host is up)

Only one new record; nothing else on 1on1realtors.com changes (the apex and `www` stay on the Lovable site).

- **Fly:** run `fly certs add bop.1on1realtors.com -a bop-1on1realtors`, then add
  `bop  CNAME  bop-1on1realtors.fly.dev` (TTL 300). If the zone is on Cloudflare, set the record to
  **DNS only** (grey cloud) so Fly can issue the certificate; `fly certs show` confirms it.
- **Render:** add the custom domain in the service's settings, then `bop  CNAME  bop-1on1realtors.onrender.com`
  (DNS only on Cloudflare); Render issues the certificate.
- After it resolves: confirm `https://bop.1on1realtors.com/api/health` answers `{"bops":true}` and that
  `https://bop.1on1realtors.com/` redirects to Google sign-in.

## WhatsApp export reader (realty/, Si.Clienty's daily job)

WhatsApp groups aren't read by a bot (that breaks WhatsApp's terms). Instead someone uses WhatsApp's
own **Export chat** (without media is fine) on each group once a day and drops the `.zip` or `.txt` in
a Drive folder in the 1on1 Realtors account. Then:

```sh
npm run realty:wa                      # reads new files in ONEON1_WA_DRIVE_FOLDER_ID
npm run realty:wa -- --file chat.zip   # or a file on this machine
```

It parses both iPhone and Android layouts, finds leads (name, phone, email, budget, area, what kind of
property, buy or rent) and action items (asks like "please call…", "can someone schedule a viewing…",
with @mentions and due days), merges repeat mentions of the same person, dedupes against the CRM
(`crm_clients` via the read-only view below, `contact_submissions`, `property_inquiries`; phone or
email = duplicate, name only = possible duplicate), and writes `proposals.json` + `proposals.md` under
`.data/realty/whatsapp/<run>/` (mode 0600). It prints counts only. A file or proposal it has handed
over once is not proposed again (`ledger.json`).

Nothing is written to the CRM. To write, a person sets `"approved": true` on proposals and runs
`npm run realty:wa -- --apply <run>/proposals.json` with `ONEON1_CRM_WRITES=1`. The writer only inserts
into `contact_submissions` (a lead with an email) or `crm_tasks` (a lead with only a phone, or a to-do,
assigned to the agent who posted it, the @mentioned agent, or `ONEON1_DEFAULT_AGENT_ID`), only the
columns it proposed, once per proposal. Without the flag it's a dry run.

## Agent inbox sorter (realty/inbox.ts, off by default)

For each agent who agrees and connects their Gmail, it sorts new mail into **lead / viewing request /
offer / follow-up / other** and proposes: a CRM record (new lead → `contact_submissions`; anything else
→ a `crm_tasks` task for that agent), an Asana task (`ONEON1_ASANA_PROJECT_ID`; proposed only, never
created), and a reply drafted in the agent's name with blanks for them to fill.

```sh
ONEON1_INBOX_SORTER=1 npm run realty:inbox            # all agents in ONEON1_INBOX_AGENTS, last 2 days
npm run realty:inbox -- --agent kerry --days 7
```

It never sends. Drafts stay in `proposals.md` unless `ONEON1_INBOX_GMAIL_DRAFTS=1`, which also saves them
in the agent's own Gmail Drafts (needs the `gmail.compose` scope) for them to edit and send. Gmail is read
through Google's API with the agent's own refresh token (`ONEON1_GMAIL_REFRESH_TOKEN_<SLUG>`,
`gmail.readonly`); Composio (already in Bops) is the alternative if agents would rather connect there.

Rules are plain keyword rules (no AI), so the same mail always sorts the same way and each proposal lists
why. Moving the sorting to the bots' model is a later step once agents have seen how it does.

## CRM read access for crm_clients

The bot login's `admin` role can't read `crm_clients` (RLS: super admin or the owning agent).
`docs/1on1-crm-readonly.sql` is a **draft, not applied** read-only view for the bot only. Until it's
applied, dedupe skips `crm_clients` and says so.

## Lead flow v1 (realty/flow/, dry run only)

Every new inquiry (website contact form, property inquiry, WhatsApp) is acknowledged to the client at once,
routed to one agent, and that agent is alerted with listing matches. If they don't accept in time, one backup
gets it. If the backup misses too, it becomes an admin exception. Admin sees only exceptions and one daily
report; nothing waits for admin. **Nothing is sent**: every message is appended to `.data/realty/outbox.jsonl`
and printed. The outbox has no transport.

Run the demo on a simulated day against the fixture CRM (`realty/fixtures/crm.json`, made-up people):

```sh
npm run realty:demo     # resets .data/realty/outbox.jsonl and lead-flow-state.json first
npm run realty:test
npm run realty:typecheck
```

Routing: the listing's agent if the inquiry names a listing; otherwise the agents who cover the area and
listing type, the one with fewest open leads (lower agent id on a tie). Each lead gets at most two offers:
the assigned agent, then one backup. A pass moves it on at once. The routing rules are in `realty/flow/route.ts`.

Config (environment, all optional):

- `ONEON1_LEAD_TIMEOUT_MINUTES`: answer window per agent, default `15` (1 to 240).
- `ONEON1_MARKET_SEARCH_URL` and `ONEON1_MARKET_SEARCH_TOKEN`: both needed, or the search is off. When on, the
  flow calls `search_market_listings` on tt-market-search (Streamable HTTP) for buyers and renters with criteria,
  and lists other agencies' hits as co-broke candidates in the agent's alert. Our own listings are dropped.
  Each request times out after `ONEON1_MARKET_SEARCH_TIMEOUT_MS` (default 4000); on failure the alert says
  "not checked" and the flow carries on. It sends the server's own arguments (`listing_type`, `area`,
  `beds_min`, and `price_max` only for a TTD budget, since the index mixes TTD and USD). Checked against a
  local tt-market-search server on 12 Nov 2026.

Not yet, before this can go live:

- A live CRM adapter for the `CrmSource` interface (`realty/flow/source.ts`), reading through the read-only
  connector in `realty/crm.ts`, plus a source of new inquiries (poll or webhook).
- A timer that calls `tick()` (the flow has none yet; the demo advances the clock by hand).
- Parsing agents' replies (ACCEPT / PASS) from WhatsApp or email. The demo calls `respond()` directly.
- Real transports, each approved by the owner, starting with admin only.
- Hosting and a single state store (the CLI writes a JSON file; the hosted app doesn't use it yet).
