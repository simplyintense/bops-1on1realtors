# 1on1 Realtors setup

This fork runs Bops for 1on1 Realtors (1on1realtors.com, Trinidad and Tobago).

## The team (lib/realty-team.ts)

A fresh start (or Start over) gets five bots, all on the main bot's computer. Names use the
Si.<Function> style for Simply Intense business bots.

| Bot | Role | What it does |
|---|---|---|
| Si.Leady (main, id `boppy`) | Lead bot, 1on1 Realtors | Takes requests and hands them to the specialists |
| Si.Clienty (id `clienty`) | Client and lead intake | New website leads (contact form + property inquiries), flags ones waiting over 24h, drafts first replies |
| Si.Listingy (id `listingy`) | Listings | Stale, unviewed or incomplete listings; matches CRM clients to listings |
| Si.Viewy (id `viewy`) | Viewings and showings | Tour/viewing requests, clashes, drafts confirmations |
| Si.Reporty (id `reporty`) | Weekly report | Monday report: leads, showings, clients, tasks, listings (facts only) |

`BOPS_TEAM_PRESET=bops` brings back upstream's Boppy alone. Nobody is contacted without the owner's OK.

## The CRM connector (lib/server/realty-crm.ts) — read-only stub

The realty_* tools (`realty_new_leads`, `realty_listings`, `realty_showings`, `realty_pipeline`) read the
site's Supabase backend over its REST API, signed in as a dedicated bot login so the CRM's row-level
security decides what they see. They are only offered when all of these are set in `.env.local`:

- `ONEON1_CRM_URL`, `ONEON1_CRM_ANON_KEY` (publishable key only, never the service-role key)
- `ONEON1_CRM_BOT_EMAIL`, `ONEON1_CRM_BOT_PASSWORD`

The chat tools never write. `ONEON1_CRM_WRITES=1` only lets the realty CLIs' `--apply` step insert
approved proposals (below). Wired into chat turns; computer tasks don't get
them yet.

## Hosting at bop.1on1realtors.com (not deployed yet)

The same Next server the Mac app ships, in a container (`Dockerfile`), with a login gate in front.
Two ready configs; pick one host:

- **Fly.io** (`fly.bop-1on1.toml`, region `mia`, 3 GB volume for `.data/`, one always-on machine):
  ```sh
  fly apps create bop-1on1realtors
  fly volumes create bops_data --size 3 --region mia -a bop-1on1realtors
  fly secrets set -a bop-1on1realtors BOPS_ALLOWED_EMAILS=... BOPS_GATE_SECRET=... GOOGLE_OAUTH_CLIENT_ID=... \
    GOOGLE_OAUTH_CLIENT_SECRET=... ORGO_API_KEY=... OPENAI_API_KEY=... OPENAI_EXECUTOR_API_KEY=... \
    ONEON1_CRM_URL=... ONEON1_CRM_ANON_KEY=... ONEON1_CRM_BOT_EMAIL=... ONEON1_CRM_BOT_PASSWORD=...
  fly deploy -c fly.bop-1on1.toml
  ```
  (Type the values in a terminal or the Fly dashboard. Never put them in this repo, a PR or a chat.)
- **Render** (`render.yaml`, a Blueprint: Docker web service + 3 GB disk). Secrets are `sync: false`,
  entered in Render's dashboard; `BOPS_GATE_SECRET` is generated by Render.

One instance only on either host: the state is a file on the volume, which two instances can't share.
(Upstream's Postgres mode, `BOPS_DATABASE_URL`, is for Bops Cloud's own multi-user hosting and isn't
used here.)

### The login gate (lib/gate.ts, proxy.ts, app/api/gate/*)

`BOPS_LOGIN_GATE=google` (set in the image) puts Google sign-in in front of every page and API call.
Only emails on `BOPS_ALLOWED_EMAILS` get in (exact addresses, or `@1on1realtors.com` for the whole
domain); the list is checked on every request, so removing someone and restarting signs them out.
Sessions last 12 hours, in an httpOnly, Secure, SameSite=Lax cookie signed with `BOPS_GATE_SECRET`.
If the gate is on but a setting is missing, the server answers 503 to everyone (fails closed).
Open without sign-in: `/api/health` (says only `{"bops":true}`), the sign-in routes, and the webhook
paths that check their own signatures (`/api/apps/call`, `/api/phone/*`, `/api/channels/slack/events`,
`/api/cloud/event`, `/api/intake/periskope`). The Periskope staff paths (`/api/intake/periskope/opt-out`,
`/api/intake/periskope/consent`) stay behind the gate. With the gate off (the Mac app, `npm run dev`),
nothing changes from upstream.

Google OAuth client (in the 1on1 Realtors Google Cloud project): type "Web application", authorized
redirect URIs `https://bop.1on1realtors.com/api/gate/callback` and, until DNS is live,
`https://bop-1on1realtors.fly.dev/api/gate/callback` (or the onrender.com name). Scopes: `openid email`.

## WhatsApp export reader (realty/, Si.Clienty's daily job)

WhatsApp groups aren't read by a bot (that breaks WhatsApp's terms). Instead someone uses WhatsApp's
own **Export chat** (without media is fine) on each group once a day and drops the `.zip` or `.txt` in
a Drive folder in the 1on1 Realtors account. Then:

```sh
npm run realty:wa                      # reads new files in ONEON1_WA_DRIVE_FOLDER_ID
npm run realty:wa -- --file chat.zip   # or a file on this machine
```

It parses both iPhone and Android layouts, finds leads (name, phone, email, budget, area, what kind of
property, buy or rent) and action items (asks like "please call…", "can someone schedule a viewing…",
with @mentions and due days), merges repeat mentions of the same person, dedupes against the CRM
(`crm_clients` via the read-only view below, `contact_submissions`, `property_inquiries`; phone or
email = duplicate, name only = possible duplicate), and writes `proposals.json` + `proposals.md` under
`.data/realty/whatsapp/<run>/` (mode 0600). It prints counts only. A file or proposal it has handed
over once is not proposed again (`ledger.json`).

Nothing is written to the CRM. To write, a person sets `"approved": true` on proposals and runs
`npm run realty:wa -- --apply <run>/proposals.json` with `ONEON1_CRM_WRITES=1`. The writer only inserts
into `contact_submissions` (a lead with an email) or `crm_tasks` (a lead with only a phone, or a to-do,
assigned to the agent who posted it, the @mentioned agent, or `ONEON1_DEFAULT_AGENT_ID`), only the
columns it proposed, once per proposal. Without the flag it's a dry run.

## Agent inbox sorter (realty/inbox.ts, off by default)

For each agent who agrees and connects their Gmail, it sorts new mail into **lead / viewing request /
offer / follow-up / other** and proposes: a CRM record (new lead → `contact_submissions`; anything else
→ a `crm_tasks` task for that agent), an Asana task (`ONEON1_ASANA_PROJECT_ID`; proposed only, never
created), and a reply drafted in the agent's name with blanks for them to fill.

```sh
ONEON1_INBOX_SORTER=1 npm run realty:inbox            # all agents in ONEON1_INBOX_AGENTS, last 2 days
npm run realty:inbox -- --agent kerry --days 7
```

It never sends. Drafts stay in `proposals.md` unless `ONEON1_INBOX_GMAIL_DRAFTS=1`, which also saves them
in the agent's own Gmail Drafts (needs the `gmail.compose` scope) for them to edit and send. Gmail is read
through Google's API with the agent's own refresh token (`ONEON1_GMAIL_REFRESH_TOKEN_<SLUG>`,
`gmail.readonly`); Composio (already in Bops) is the alternative if agents would rather connect there.

Rules are plain keyword rules (no AI), so the same mail always sorts the same way and each proposal lists
why. Moving the sorting to the bots' model is a later step once agents have seen how it does.

## Lead flow v1 (realty/flow/, dry run only)

Every new inquiry (website contact form, property inquiry, WhatsApp) is acknowledged to the client at once
(from the brand, "1 On 1 Realty"), routed to one agent, and that agent is alerted with listing matches.
Matches wait for the agent's approval before a client message is even drafted. If the agent doesn't accept
in time, one backup gets it. If the backup misses too, it becomes an admin exception, and admin can reassign
it. Daily and weekly reports go to admin. **Nothing is sent**: every message is recorded in the dry-run
outbox (the demo CLI also appends it to `.data/realty/outbox.jsonl` and prints it). The outbox has no transport.

Run the demo on a simulated day against the fixture CRM (`realty/fixtures/crm.json`, made-up people):

```sh
npm run realty:demo     # resets .data/realty/outbox.jsonl and lead-flow-state.json first
npm run realty:test
npm run realty:typecheck
```

Routing: the listing's agent if the inquiry names a listing; otherwise the agents who cover the area and
listing type, the one with fewest open leads (lower agent id on a tie). Each lead gets at most two offers:
the assigned agent, then one backup. A pass moves it on at once. The routing rules are in `realty/flow/route.ts`.

Config (environment, all optional):

- `ONEON1_ACK_SENDER_NAME`: who client messages (acknowledgement, approved matches) come from. Default
  `1 On 1 Realty`. Always the brand, never an individual agent.
- `ONEON1_BUSINESS_HOURS` (`08:00-17:00`) and `ONEON1_BUSINESS_DAYS` (`mon-fri`): the hours the answer window
  counts in, Port of Spain time. **PLACEHOLDER**: until Wendy/Crystal confirm the real hours, the default is
  Monday to Friday 08:00-17:00, and every report and `deskView` carries `hours.placeholder: true`. It turns
  false only when both are set and valid.
- `ONEON1_LEAD_TIMEOUT_MINUTES`: answer window per agent, default `15` (1 to 240), counted in business time
  (an inquiry at 16:50 Thursday is due 08:05 Friday).
- `ONEON1_CRM_URL`, `ONEON1_CRM_ANON_KEY`, `ONEON1_CRM_BOT_EMAIL`, `ONEON1_CRM_BOT_PASSWORD`: the live CRM,
  read through `realty/flow/live-crm.ts` (`crmSourceFromEnv`, read-only; it takes a fallback source, e.g. the
  fixture, for when they aren't set). `ONEON1_CRM_WRITES` stays off for the lead flow: it never writes to the CRM.
- `ONEON1_MARKET_SEARCH_URL` and `ONEON1_MARKET_SEARCH_TOKEN`: both needed, or the search is off. When on, the
  flow calls `search_market_listings` on tt-market-search (Streamable HTTP) for buyers and renters with criteria
  (and `resolve_area` for area names; see "Geography matching"),
  and lists other agencies' hits as co-broke candidates in the agent's alert. Our own listings are dropped.
  Each request times out after `ONEON1_MARKET_SEARCH_TIMEOUT_MS` (default 4000); on failure the alert says
  "not checked" and the flow carries on. It sends the server's own arguments (`listing_type`, `area`,
  `beds_min`, and `price_max` only for a TTD budget, since the index mixes TTD and USD). Checked against a
  local tt-market-search server on 12 Nov 2026.

Matches and management-only messages:

- Listing matches go to the agent's alert (internal) and wait in an approval queue
  (`flow.pendingApprovals()`). Only `approveMatches(id, selectedIds)` records a client message, and only as a
  dry-run `client_match` from the brand. `rejectMatches(id)` (or an empty selection) records nothing.
- A management-only message (complaints, commissions/invoicing, price or contract changes, compliance
  documents, unusual deals; `realty/flow/management.ts`) is never acted on: no acknowledgement, no routing,
  only an admin exception whose reason starts `management-only:`.

### Geography matching (realty/flow/areas.ts, match.ts, area-learning.ts)

Area matching is by tier, not by exact text alone. For a buyer or renter who names an area, each listing
(ours, or another agency's co-broke hit) gets one tier, and the agent's alert gives the reason on its line:

| Tier | Reason text (example) | When |
| --- | --- | --- |
| same-area | `same area: Westmoorings` | the two names resolve to the same canonical area |
| neighbour | `nearby: Glencoe for Westmoorings` | one area lists the other as a neighbour (listing area named first) |
| same-region | `same region: North West` | both are in the same region |
| excluded | `excluded: Tobago vs Trinidad`, or `excluded` | anything else; dropped |

Candidates are ranked by tier, then, inside the neighbour tier, by the neighbour's market weight (higher first), then by price. Budget, beds, type, status and "not the listing
asked about" are checked as before. Co-broke hits are filtered and ranked the same way, client-side: the search
server's area filter is not trusted as a geography check.

**Regions** (exact strings): `Port of Spain`, `North West`, `East–West Corridor`, `Central`, `South`, `Tobago`.

**The Tobago/Trinidad rule.** The island is market-mcp's `island` (`"Tobago"` or `"Trinidad"`). When that's absent,
it comes from the region: `Tobago` is Tobago, every other region is Trinidad. A Tobago area never matches a
Trinidad one, even if a neighbour list says so. The island check runs first, so a wrong neighbour list can't cross
islands. A region the code doesn't know, with no island, isn't claimed for either island.

**Neighbour weights.** market-mcp gives each neighbour a weight. Inside the neighbour tier, a higher weight ranks
first, then the cheaper price. If two areas list each other, the higher of the two weights is used. A neighbour
named with no weight counts as 0. The weight is on the ranked row; the alert shows only the reason.

**Where the names come from, in order** (`CompositeAreaResolver`, one per flow, cached per flow):

1. Local staff aliases (`.data/realty/areas/aliases.jsonl`). An alias's canonical name is then looked up on the
   market for its region, island and neighbours.
2. `resolve_area` on market-mcp, when `ONEON1_MARKET_SEARCH_URL` and `_TOKEN` are both set. A confidence of 0.8 or
   more maps the text. A confidence below 0.8, or `area: null` (unresolved), is **unmapped**, and the answer's
   suggestions go to the desk.
3. Exact text (case and spacing only, no region, no neighbours). This is used only when the market is down,
   times out, or isn't set. A timeout or error starts a 60-second cooldown, so a slow market doesn't stall every
   area in an alert. An unmapped answer from a working market stays unmapped; identical text still matches
   itself, and nothing else does.

With the market off, matching is today's exact text, and the alert's reasons read `same area: …`.

**Unmapped areas.** An inquiry area or an active CRM listing area the resolver doesn't recognise is unmapped.
- On the desk (`deskView`): `unmappedAreas` gives `count` (distinct areas) and up to 10 `examples` (`text`,
  `occurrences`, `from`: inquiry and/or listing, and `suggestions` from an unmapped answer). Each lead has
  `unmappedArea: true` and `suggestions` when its inquiry area is unmapped. This is a missing-field flag on the
  lead. It is not a management exception, and it doesn't go on Wendy's listing missing-fields list.
- Staff map an alias once with the staff-only API below.

**Staff alias API** (behind the login gate, not an open path; 403 on the public demo):

```
POST /api/realty/areas/alias     { "alias": "Westmoring", "canonical": "Westmoorings" }
→ 201 { "alias": { "alias", "canonical", "at", "market": "dry-run" | "sent" | "failed" } }
→ 400 for a bad body (text, 1 to 80 characters each)
```

The row goes to `.data/realty/areas/aliases.jsonl` (0700 directory, 0600 file). The last row for an alias wins.
The same mapping is posted to market-ingest (see "Market calls" below), and the row's `market` field records the
outcome. Local aliases are checked first on every resolve. The handler is `mapAreaAlias` (`realty/node/area-store.ts`), and
the gate is `staffAccess` (`realty/node/periskope-intake.ts`).

**Learning (data collection only; no tier changes yet).** Only an explicit staff or agent decision records anything:

- `approveMatches(id, selectedIds)`: one record per **selected** candidate, `approved`. Candidates left out are
  not recorded at all, so they aren't treated as rejected.
- `rejectMatches(id)`, or an empty selection: one record per candidate in that approval, `rejected`.
- A record is `{ inquiryArea, listingArea, tier, signal, at }` in `.data/realty/areas/pairs.jsonl`. Candidates
  with no inquiry area, no listing area, or tier `any` are not recorded.
- The desk's `areaLearning` counts records by signal, by tier and by pair.
- Nothing is sent on receive, on `tick()`, or in bulk. Nothing replays history.
- Learning is local only. It makes no market call and changes no tier or weight. Automatic neighbour-weight changes
  wait until Miles approves them. The TODO in `realty/flow/area-learning.ts` marks the future market-ingest
  `kind: "neighbour"`.

**Market calls.** The flow calls market-mcp for two things only, through the same MCP client
(`MarketClient.callTool` in `realty/flow/market-search.ts`): `search_market_listings` and `resolve_area`. It never
calls a `learn_` tool. A staff alias goes to market-ingest instead, as one POST:

- `POST ONEON1_MARKET_WRITE_URL` with `Authorization: Bearer ONEON1_MARKET_INGEST_TOKEN` and the flat body
  `{ "kind": "alias", "alias": "Westmoring", "canonical": "Westmoorings" }` (`aliasItem` in `realty/flow/periskope.ts`).
- **Dry run** (no network) unless `ONEON1_MARKET_WRITE_URL`, `ONEON1_MARKET_INGEST_TOKEN` and `ONEON1_MARKET_ALIAS_WRITE`
  (`1` or `true`) are all set. The market search URL and token don't switch it on. The flag is alias-only: market-ingest
  does not accept `kind: "alias"` yet. The write URL and token alone still post listings, requests and groups, but not aliases.
- One attempt, no retry. A success gives `market: "sent"`; a failure gives `market: "failed"`. The mapping is kept
  either way, and the request still succeeds.

**Confirmed market-mcp shape (from Builder, tt-market-search).** The flow reads it in `areaFromToolResult` and
`neighbourList` (`realty/flow/areas.ts`).

- `resolve_area`, args `{ text }`. Response: `{ area, island, region, municipality, neighbours: [{ area, weight }],
  confidence, suggestions }`, where `confidence` is always a number from 0 to 1. A plain name in `neighbours` is
  accepted with weight 0 (for fixtures). The JSON may be the second text block of the result, or `structuredContent`.
- An unrecognised name: `{ area: null, unresolved: true, suggestions }`. That's unmapped, and `suggestions` go to the
  desk.
- A string `"high"` or `"low"` confidence is also read, for old fixtures only.

**Not used by the flow:** the `candidates` field, `learn_area_alias` and `learn_area_neighbour` (the neighbour shape
there is now `{ areaA, areaB, delta }`).

Reports: `sendDailyReport()` (every lead the flow holds) and `sendWeeklyReport()` (leads received in the 7
days up to now) go to admin as one dry-run email each. Besides per-agent responsiveness, exceptions and open
leads, they count enquiries by property kind and channel, list management-only leads, and list our active
listings missing information a client needs (with the missing field names).

### Portable core and the staff desk (planned on Lovable)

The staff back office is planned on **Lovable** (Vite/React + Supabase), not as a Next.js app. The lead-flow
core is plain TypeScript with no Next.js and no Node-only imports, so it can run in a Supabase (Deno) edge
function, a browser bundle or Node alike:

- Portable: `realty/flow/{engine,flow,hours,listing-audit,live-crm,management,market-search,match,messages,
  outbox,report,route,source,taxonomy,desk,env,demo-day,periskope,areas,area-learning}.ts` and `realty/crm.ts`. No `node:*`, no `next/*`,
  no bare `process` (`env.ts` `runtimeEnv()` reads `globalThis.process?.env` if there is one, else `{}`; on
  Deno pass `Deno.env.toObject()` to the `*FromEnv(env)` helpers). `realty/test/desk.test.ts` checks this.
- Injected: the CRM source (`CrmSource`; `FixtureCrm.from(data)` or the fetch-based `LiveCrmSource`), the clock,
  the outbox (`Outbox`; `DryRunOutbox({ clock, append?, print? })` hands each message to `append` as one
  JSONL line), and state (`persist(snapshot)` / `snapshot`).
- Node-only helpers live in `realty/node/jsonl.ts`: `appendJsonl` / `jsonlAppender(file)` for the CLI's
  outbox file, and `loadFixtureCrm()` for the fixture JSON.
- `deskView(input)` (`realty/flow/desk.ts`) is the JSON contract a UI reads: `generatedAt`, `dryRun: true`,
  `ackSender`, `hours` (with `placeholder`), `slaMinutes`, `queue` (`open`, `escalations`, `exceptions`,
  `overdue`: each lead's state, deadline, agent, channel, kind, management flags), pending `approvals` with
  their candidates, `missingFields`, `summary` (`daily`, `weekly`, `tally`), `managementOnly`, the dry-run
  `outbox`, and `log`. `flowDesk(flow)` builds it from a running `LeadFlow`. Pure: no clock, no I/O.
- Timeouts move on only when the host calls `flow.tick()` (it returns how many offers ran out). There is no
  timer in the flow and none in `instrumentation.ts`; the Lovable/Supabase side would call it on a schedule
  (e.g. a cron'd edge function every minute) and persist the snapshot. `tick()` also runs `onTick` (the
  Periskope host wires the retention purge and one market-outbox flush here).

The Next `/realty-demo` page stays the public fixture demo only. The lead flow's desk is still planned on Lovable;
the Next staff pages are a thin landing and one read-only tool (below).

**Staff desk (`/realty/desk`, staff only).** The landing page, with a shared staff nav (Desk, Market search, and
"Back to Bops" to `/`). It's behind the login gate like every page, the public demo redirects it, and it's not indexed.

**Market search (`/realty/market`, staff only, read-only, linked from the desk).** Other agencies' listings for an
area, from the same market as the co-broke matches. Filters are GET query params, so the market token never reaches
the browser:

- Area: free text, resolved the same way as matching (local aliases, then `resolve_area`, then exact text). The page
  shows what it resolved to. With "Include nearby areas" on, the canonical area and its neighbours are searched and
  de-duplicated by url (or title and source); off, only the canonical area. An unknown area is searched as typed and says so.
- Beds and price: `beds_min` and a TTD `price_max` go to `search_market_listings`. `beds_max`, `price_min`, and price
  bounds for USD listings are checked on the page. "Any" currency is read as TTD for the cap; each listing shows its own currency.
- Listing type is sale or rent only (the one type the market supports).
- Results: title, agency, area, beds, baths, price, last seen (when the hit has `last_seen`, else "—"), and a link to
  the source listing in a new tab (only http or https). Our own listings (`oneonone`) are not shown.
- States: nothing searched yet; "not configured" (search is off until `ONEON1_MARKET_SEARCH_URL` and
  `ONEON1_MARKET_SEARCH_TOKEN` are set on the server, with no values shown); no matches; "timed out" or "unavailable".
  A search where some areas fail still shows the rest, with a warning.
- Never writes: no alias, no `learn_area_neighbour`, no CRM write, no send. Only `search_market_listings` and
  `resolve_area` are called. The helper is `marketDeskSearch` (`realty/flow/market-desk.ts`), with the server's
  settings from `staffMarketSearch` (`realty/node/market-desk.ts`); the lead flow's five-hit cap is unchanged.

The same search is the staff-only JSON API `GET /api/realty/market/search?area=…&nearby=1&bedsMin=…&priceMax=…&currency=TTD`
(`staffAccess`: 403 on the demo, 401 without a session, 503 if the gate is misconfigured). It answers 200 with `status`
`ok` or `not-configured`, and 502 with `status: "error"` when the market fails.

The other Next route under `/api/realty/*` is the staff alias API above (`app/api/realty/areas/alias`), which the desk
doesn't use yet.

### Periskope intake (read-only, sends off)

`POST /api/intake/periskope` receives Periskope's `message.created` webhooks for WhatsApp groups. The
signature is HMAC-SHA256 of the raw body, hex, in the `x-periskope-signature` header, checked with
`PERISKOPE_SIGNING_KEY` ([Periskope webhook docs](https://docs.periskope.app/api-reference/webhooks/introduction)).
The key unset answers 503; a missing or wrong signature answers 401. Everything accepted or ignored
(wrong event, sent by us, not a group, no consent, opted out, media or non-text, already seen, chatter)
answers 200 quickly. Bops never posts or replies to WhatsApp and never calls the Periskope API.

A buyer request is taken into the existing lead flow (`source: periskope-group`, `channel: whatsapp`)
so the SLA, missing-field flags, matching and approval queue run unchanged, and is also queued for
market-ingest as `kind: "request"`. A co-broke listing is queued as `kind: "listing"`. A staff area alias is
posted as `kind: "alias"` (see Geography matching). Chatter is
dropped. Nothing stores the raw message text: only the buyer brief or listing details (budget, area,
type, beds) and the posting agent's business name and number.

The market-ingest adapter POSTs one item at a time to `ONEON1_MARKET_WRITE_URL` (the
`/functions/v1/market-ingest` URL) with `Authorization: Bearer` from `ONEON1_MARKET_INGEST_TOKEN`. It
stays dry-run (records only) unless both are set. A `403` `not_allowlisted` or `opted_out` is logged
and not retried. Network errors stay on the outbox and are retried later by `tick()` / `flushMarketOutbox`,
never inline. Item payloads do not include a consent field; the group is allowlisted with a separate
`kind: "group"` post (see Consent). The write contract is in HOSTING.md on
[tt-market-search PR #3](https://github.com/simplyintense/tt-market-search/pull/3) (commit 8867403).

Config:

- `PERISKOPE_SIGNING_KEY`: required for the webhook to accept posts.
- `PERISKOPE_ALLOWED_CHATS`: optional extra comma-separated chat ids. Empty or unset means consent
  records alone decide (an empty list is not "accept none").
- `PERISKOPE_REQUEST_RETENTION_DAYS`: default `60` (buyer requests and their seen metadata).
- `PERISKOPE_LISTING_RETENTION_DAYS`: default `90` (WhatsApp co-broke listings and their seen metadata).
- `ONEON1_MARKET_WRITE_URL` and `ONEON1_MARKET_INGEST_TOKEN`: both needed, or the adapter stays off.
- `ONEON1_MARKET_ALIAS_WRITE`: `1` or `true` to let staff aliases post (`kind: "alias"`). Off by default; see Geography matching.

`purgeExpiredPeriskope` is callable on its own and from `LeadFlow.tick()` via `onTick`.

### Live matching (realty/flow/live-match.ts, crm-seam.ts)

Every buyer request the intake takes is stored as a live request (`live-matches.jsonl`: structured facts and
the posting agent's number, never the text) and matched once on arrival with the market's read-only
`match_buyer` tool. The co-broke rules are the market's (same island, same or neighbouring area, price within
20%, beds within one, sale vs rent, type); Bops keeps the top five with the market's reason line and drops
scores (1on1 scoring isn't decided yet). This works with no CRM: the lead flow still runs only when a CRM is
set up. Seen is marked before matching, so a slow or failed match never stores a request twice; the status
(`matched`, `no-intent`, `not-configured`, `timeout`, `unavailable`) is kept on the row. Opt-out and the request
retention window remove live rows too.

The desk shows each agent "Matches for your WhatsApp requests" (by the agent's number from the CRM seam).
Requests not tied to one of our agents, and other agencies' open requests from the market, are for owners
(`BOPS_OWNER_EMAILS`) only. `/realty/digest` is the owners' daily digest (last 24 hours) with a
"Replay sample WhatsApp messages" button (`POST /api/realty/replay`, owners only): the samples in
`realty/fixtures/whatsapp-samples.ts` go through the signed webhook path into a temp store with
market-ingest off; nothing is kept or sent.

The CRM seam (`crm-seam.ts`) is where the CRM plugs in: `listings()` for our own listings and `agents()` for
agent email and WhatsApp number. It is `NOT_CONNECTED` until the read-only CRM adapter is wired in, so the desk
says "CRM not connected" and every WhatsApp request shows as unassigned to owners.

Node helpers live in `realty/node/periskope-store.ts` and `realty/node/periskope-intake.ts` (signature,
store, outbox, staff functions). The staff routes are `/api/intake/periskope/consent` and
`/api/intake/periskope/opt-out`.

### Consent

Staff post the group's WhatsApp notice by hand. Bops never posts into a group. A group's messages are
accepted only once a persisted consent record in `.data/realty/periskope/` has both `noticePostedAt`
and `adminOkAt` set, and `active` is not false. Staff record that with `POST /api/intake/periskope/consent`
(`chatId`, `groupName`, `noticePostedAt`, `adminOkBy`, `adminOkAt`, `active`). `adminOkBy` is a business
name or role, never a phone number (the route rejects a number).

When both the notice and the admin's OK are first set, Bops also POSTs `kind: "group"` to market-ingest
with: `group` (the WhatsApp `chat_id`, the same value sent as `group` on every listing/request item),
`name`, `noticePostedAt`, `adminOkAt`, `adminOkBy`, and `active: true`. The response is
`{ group, active, adminOk }`. Revoke by sending `active: false` (not by clearing `adminOkAt`); later
listing or request posts for that group are refused by market-ingest as `not_allowlisted`, and Bops
stops accepting its messages.

Opt-outs: `POST /api/intake/periskope/opt-out` with `{ senderPhone }` adds the number to a persisted
list, deletes everything already stored from that sender (leads from this route, market-ingest source
items, seen-id metadata), and POSTs `kind: "optout"` (with `senderHash` of the number) to market-ingest.
Later messages from that sender are dropped before the body is parsed.
